## Замечания

### RR1 — P2: проверка lineage ломает reconcile с corrections из derived-снимка

Место: `src/alpha_lab/reconcile.py:117–118`; предположение о схеме manifest — `src/alpha_lab/pipeline.py:110`.

Новый вызов check_vintage_lineage предполагает, что любой каталог corrections.json с manifest является correction vintage и содержит metadata.reconciliation_snapshot. Однако build сохраняет corrections.json также в derived-снимке; его manifest содержит source_manifest_sha256 и corrections_vintage. Передача такого файла в reconcile теперь заканчивается `KeyError: 'reconciliation_snapshot'`, хотя файл исправлений и привязка к источнику корректны. API принимает путь к corrections.json, а docstring reconcile описывает повторную сверку исправленного vintage.

Воспроизведение без записи в реальный журнал:

```python
from pathlib import Path
from alpha_lab.pipeline import check_vintage_lineage
from alpha_lab.provenance import sha256

root = Path.cwd()
source = root / 'data/snapshots/20261006T103809-a4a22ec667'
derived = root / 'data/derived/20261006T172442-80ef993493'
check_vintage_lineage(root, sha256((source / 'manifest.json').read_bytes()),
                      derived / 'corrections.json', None)
# KeyError: 'reconciliation_snapshot'
```

Оба corrections.json, из derived и `data/corrections/20261006T172434-fbb5c9f554`, побайтно одинаковы. Manifest derived проверен, его source_manifest_sha256 совпадает с источником. Дополнительно построена синтетическая цепочка source → reconcile → corrections → audit в отдельном временном каталоге. На её derived/corrections.json прежняя реализация reconcile из `ae2cd38` завершает сверку, CCC получает confirmed; текущая реализация падает с указанным KeyError. Прочие модули в сравнении одинаковы. Таким образом, это регрессия reconcile в проверяемом диапазоне. Аналогичное ограничение audit существовало раньше.

Предлагаемое исправление: различать manifest correction vintage и derived-снимка. Для derived проверить source_manifest_sha256, целостность corrections.json и его соответствие записанной ссылке/хешу исходного correction vintage; затем проверить происхождение этого vintage. Не обходить проверку происхождения при отсутствии ожидаемого поля. Добавить тест успешной повторной сверки с derived/corrections.json, а также отказов при другом source snapshot и несогласованных ссылках/хешах. Существующий тест R3 сохранить. Проверенный рабочий путь через data/corrections остаётся доступен.

### RR2 — P3: неверное пустое значение payable_date незаметно превращается в отсутствие даты

Место: `src/alpha_lab/normalize.py:88`.

Условие по истинности значения не различает `None` и неверный тип. Для replace события TEST 2017-11-29 с yahoo_amount=0.4, issuer_amount=0.45, source='ref' значения payable_date `False`, `0`, `''`, `[]`, `{}` принимаются; результат — 2017-12-11 с basis=proxy_ex_plus_10_calendar_days. Например, `norm(frame([100, 99, 98, 97], dividends=[0, .4, 0, 0]), corrections={'2017-11-29': GOOD | {'payable_date': False}})` с помощниками tests/test_normalize.py воспроизводит это поведение. Непустые неверные значения отклоняются.

Это прежний пробел в проверке входной схемы, а не новая потеря корректной даты после R2. Текущий генератор corrections выдаёт строку даты или None; в семи сохранённых исправлениях дефект не проявляется. Поэтому замечание неблокирующее.

Предлагаемое исправление: для add/replace разрешить отсутствующее поле или None как отсутствие подтверждённой даты; остальные значения проверять как строковую календарную дату до выбора actual/proxy. Добавить параметризованный тест отказа для неверных типов и пустой строки. Исходный сценарий R2 при этом остаётся закрытым.

## Пограничные случаи R2

- Дата из add и replace расширяет календарь до выбора сессии: на истории ноября–декабря 2017 payable_date=2020-01-01 даёт 2020-01-02, actual. Выходной 2017-12-02 переносится на 2017-12-04.
- Remove с заполненной payable_date не создаёт денежного события: dividend=0, поля payable_date/basis/source пусты. Дата remove игнорируется, как и раньше; расширения календаря из неё нет.
- Строки `invalid`, `2017-02-30` отклоняются с ValueError; дата раньше ex-date также отклоняется. `True`, `1`, непустой список вместо даты приводят к TypeError, результат нормализации не возвращается. Приём неверных пустых значений описан в RR2.
- При одинаковой дате и разных source приоритет получает запись payable: payable_source='payable-source', dividend_correction_source='ref'. Это две раздельные ссылки на дату выплаты и исправление суммы; потеря источника исправления не обнаружена. Исходный словарь payable не меняется. Требование отклонять разные ссылки при совпадающей дате протоколом не задано.
- Прямой normalized для реального raw-снимка с payable={} и семью corrections завершается успешно. Этот режим, используемый reconcile, теперь применяет даты исправлений; прочие события могут оставаться proxy. Сбой RR1 возникает раньше нормализации и зависит от пути к corrections.json.
