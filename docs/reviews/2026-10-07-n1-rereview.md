## Findings at the reviewed version

### RR1 — P2: lineage validation breaks reconcile with derived-snapshot corrections

Location: `src/alpha_lab/reconcile.py:117–118`; manifest-schema assumption in `src/alpha_lab/pipeline.py:110`.

The new check_vintage_lineage call assumes any corrections.json directory with a manifest is a correction vintage containing metadata.reconciliation_snapshot. However, build also saves corrections.json in a derived snapshot, whose manifest contains source_manifest_sha256 and corrections_vintage. Passing this file to reconcile raises `KeyError: 'reconciliation_snapshot'` despite valid corrections and source linkage. The API accepts a corrections.json path, and reconcile's docstring describes rechecking a corrected vintage.

Reproduction without writing to the actual journal:

```python
from pathlib import Path
from alpha_lab.pipeline import check_vintage_lineage
from alpha_lab.provenance import sha256

root = Path.cwd()
source = root / 'data/snapshots/20261006T103809-a4a22ec667'
derived = root / 'data/derived/20261006T172442-80ef993493'
check_vintage_lineage(root, sha256((source / 'manifest.json').read_bytes()),
                      derived / 'corrections.json', None)
# KeyError: 'reconciliation_snapshot'
```

The corrections.json files in derived and `data/corrections/20261006T172434-fbb5c9f554` are byte-identical. The derived manifest was verified; its source_manifest_sha256 matches the source. A synthetic source → reconcile → corrections → audit chain was also built in a separate temporary directory. For its derived/corrections.json, the former reconcile implementation from `ae2cd38` completes reconciliation and confirms CCC; the reviewed implementation raises the stated KeyError. Other modules are identical in the comparison. This establishes a reconcile regression in the reviewed range. An equivalent audit limitation existed previously.

Proposed fix at review time: distinguish correction-vintage and derived-snapshot manifests. For derived input, check source_manifest_sha256, corrections.json integrity and consistency with the recorded reference/hash of the original correction vintage; then validate that vintage's lineage. Do not bypass provenance validation when an expected field is absent. Add tests for successful reconciliation with derived/corrections.json and rejection of another source snapshot or inconsistent references/hashes. Retain the existing R3 test. The verified data/corrections path remained available.

### RR2 — P3: invalid falsy payable_date values become missing dates silently

Location: `src/alpha_lab/normalize.py:88`.

A truthiness condition does not distinguish `None` from invalid types. For replace on TEST 2017-11-29 with yahoo_amount=0.4, issuer_amount=0.45 and source='ref', payable_date values `False`, `0`, `''`, `[]` and `{}` are accepted; the output is 2017-12-11 with basis=proxy_ex_plus_10_calendar_days. For example, `norm(frame([100, 99, 98, 97], dividends=[0, .4, 0, 0]), corrections={'2017-11-29': GOOD | {'payable_date': False}})` using tests/test_normalize.py helpers reproduces the behavior. Invalid truthy values are rejected.

This was a pre-existing input-schema gap, not a new loss of a valid date after R2. The corrections generator supplies a date string or None, and the seven saved corrections are unaffected. The finding was therefore nonblocking.

Proposed fix at review time: for add/replace, allow a missing field or None to represent no confirmed date; validate every other value as a calendar-date string before actual/proxy selection. Add parameterized rejection tests for invalid types and the empty string. The original R2 scenario remains closed.

## R2 boundary cases

- Add and replace dates extend the calendar before session selection: on November–December 2017 history, payable_date=2020-01-01 produces 2020-01-02, actual. Weekend 2017-12-02 shifts to 2017-12-04.
- Remove with a populated payable_date creates no cash event: dividend=0 and payable_date/basis/source are blank. The remove date is ignored as previously and does not extend the calendar.
- `invalid` and `2017-02-30` are rejected with ValueError; a date before ex-date is also rejected. `True`, `1` and a nonempty list instead of a date produce TypeError, with no normalization result. Invalid falsy values are covered by RR2.
- With matching dates and different sources, payable takes priority: payable_source='payable-source', dividend_correction_source='ref'. These are separate references for the payment date and amount correction; no correction-source loss was found. The original payable dictionary is unchanged. The protocol does not require rejecting different references when dates match.
- Direct normalized processing of the real raw snapshot with payable={} and seven corrections succeeds. This mode, used by reconcile, now applies correction dates; other events may remain proxy. RR1 fails earlier, before normalization, depending on the corrections.json path.
